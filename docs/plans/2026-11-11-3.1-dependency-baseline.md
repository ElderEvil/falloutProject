# v3.1 Dependency Majors — Before/After Measurement Contract

**Purpose.** The v3.1 milestone ([#1258](https://github.com/ElderEvil/falloutProject/issues/1258),
milestone *3.1 Dependency Majors*) upgrades ~9 tools. Each upgrade must ship with a
**before/after** number so we upgrade on evidence, not hope. This document freezes the
*before* snapshot and defines the metric contract each *after* must reuse.

Per `docs/ROADMAP.md`, v3.1 is gated on upstream support — the point of measuring now is that
the baseline exists the moment an item becomes upgradeable.

## Method

**Automated (no infrastructure required):** `scripts/dep-baseline.py`

```bash
cd backend && uv run python ../scripts/dep-baseline.py \
    --out ../scripts/scenario_output/dep-baseline-<date>.json
```

- Every measurement runs in a **fresh interpreter** (subprocess) so import order / warm caches
  never contaminate the next value; each value is the **median of 5 samples**.
- The full-app import surface and its env-only smoke configuration are copied from
  `scripts/check_backend_image.py`; the RSS reader is copied from
  `app/tests/test_services/test_memory_regression.py`. No new instrumentation was invented.
- The pydantic probe validates a representative read model (nested list, `StrEnum`, `UUID`,
  aware `datetime`, constrained fields) 2000× and reports µs/call — a stable proxy for the
  validation hot path across pydantic majors.

**Frontend:** `pnpm run typecheck` (`vue-tsc --noEmit`) and `pnpm run build`, wall-clocked.

**Runtime rows:** measured against local infra on 2026-11-11 (see the section below) by reusing
`backend/app/tests/test_services/test_tick_perf.py` (tick wall time + statements/tick),
`game_loop_service.process_game_tick`, `TICK_PROFILE=1` (`app/core/tick_profiling.py` phase
breakdown) and `pg_stat_activity`. Do **not** add a parallel runtime harness.

### Evaluated alternative: `tsc-rs` / `tsrs` (Rust TypeScript checker)

The TS 7 blocker is Volar's need for the **TS 7.1 compiler API**. A Rust port of exactly that
revision therefore could run the type-check gate on a native checker *before* official
`tsgo` 7.1 + Vue Language Tools v4 stabilise. Assessed, **not adopted** — recorded here so the
next person does not re-open it blindly.

| Field | Value |
| --- | --- |
| Project | `pingdotgg/ts-rust` (npm `tsc-rs`), a Rust port of the TypeScript 7 compiler (MS writes it in Go); same `tsc` CLI, LSP and API |
| Package | `tsc-rs@0.8.0` (MIT AND Apache-2.0) + drop-in `@tsc-rs/typescript@0.8.0` (replaces the `typescript` package: bin, JS API, VS Code platform packages) |
| Pinned to | microsoft/TypeScript `3e9236361fa9` = **TS `7.1.0-beta`** (2026-10-19) |
| Target | Run the `typecheck` gate / `vue-tsc` on a Rust-native TS 7.1 checker |
| Gate | Same as TS 7 — Volar / Vue Language Tools v4 content-mapper support; `tsc-rs` exposes the API but Vue is its **weakest, most active** area |
| Before | `vue-tsc 3.3.13` on `typescript 6.0.3` = **5.70 s** (`pnpm run typecheck`, measured above) |
| After | *(fill only if a controlled evaluation is run)* |

**Caveats (why "evaluate," not "adopt"):** experimental, author-stated (*"I've never read a line
of this code"*); in a Vue content-mapper report a generated 3,000-component project checked in
**16.44 s vs 7.52 s for TS 7** — slower, fix pending; the project is **merging into `tsrs`**, the
Rust port now maintained by the **Oxc team** (Cloudflare, 2026-10-21); and Vite+ owns our
toolchain (`vp` provides `tsc`/`vue-tsc`), so swapping `typescript` → `@tsc-rs/typescript` fights
`frontend/AGENTS.md` and the deliberate TS 6 bridge (`docs/ROADMAP_ARCHIVE_2026-10-20.md:407-410`).

**Decision:** controlled evaluation only; prefer waiting for the Oxc `tsrs` consolidation unless
the gate must unblock sooner. Any evaluation is TS-surface only until the Volar content-mapper
path lands (`tsc-rs` cannot check `.vue` files without it).

Infra was brought up locally (PostgreSQL 18, Redis, RustFS, Mailpit). The DB held 67 vaults
(24 active) / 1394 dwellers. Backend: `uvicorn main:app` on `127.0.0.1:8000`.

| Row | Harness | Before (measured) |
| --- | --- | --- |
| API latency — uvloop (current) | `asyncio` + `httpx2`, 300 req @ C=25 → `/healthcheck` | **p50 22.8 ms, p95 35.5 ms**, mean 25.8 ms, 0 errors |
| API latency — zuvloop | same, `uvicorn --loop zuvloop` | **p50 25.8 ms, p95 40.0 ms**, mean 26.3 ms, 0 errors |

### zuvloop verdict (evaluated 2026-11-11)

zuvloop `0.0.17`, uvicorn `0.54.0`.

- **Works:** installs on linux/py3.14; `uvicorn --loop zuvloop` boots and serves; the native
  `zuvloop.cpython-314-x86_64-linux-gnu.so` is loaded in the server process; `/healthcheck`
  (touches asyncpg **and** Redis) returned 200 across 900 requests with 0 errors — the
  asyncpg/Redis compatibility the roadmap asked to check holds.
- **No win yet:** zuvloop was **~13% slower on p50** (25.8 vs 22.8 ms) and p95 (40.0 vs 35.5 ms)
  than uvloop on the identical workload.
- **Decision:** do **not** adopt — consistent with `docs/ROADMAP.md` ("benchmark … do not add it
  during the 3.0 boundary"). Re-check on a later zuvloop release / the Oxc `tsrs` consolidation.

### Environment finding (unrelated to 3.1, worth fixing)

`dramatiq_worker_infra` runs **Python 3.13** and crash-loops every tick with
`ImportError: cannot import name 'uuid7' from 'uuid'` — a stale pre-3.0 worker image. The tick
numbers above were measured by invoking the service directly, not through the worker. Rebuild it:
`podman compose -f docker-compose.infra.yml up -d --build --force-recreate --no-deps dramatiq_worker`.

## Recording an "after"

1. Apply the upgrade (one tool = one PR, per `docs/ROADMAP.md`).
2. Re-run the exact commands above; append the JSON to `scripts/scenario_output/` and fill the
   *After* cell.
3. For runtime rows, re-run the existing harness against the same seed/scale and record deltas.
4. Keep the rollback pin for the 3.1 line per #1258.
