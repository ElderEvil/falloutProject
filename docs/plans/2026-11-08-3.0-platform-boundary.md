# falloutProject 3.0 Platform Boundary — Implementation Plan

> **For Hermes:** Use `subagent-driven-development` for Phase B and D (mechanical, high-volume
> edits). Phases A, C, E, F are single-PR work and should be done directly.

**Goal:** Ship v3.0.0 — Python 3.14 runtime baseline, current Ruff/ty rule surface, aware-UTC
timestamps with SQLModel 0.0.48 / SQLAlchemy 2.1, and time-ordered UUIDv7 primary keys — as one
reversible, rehearsed maintenance boundary.

**Baseline:** v2.295.1 (`c4a9fc4`, deployed 2026-11-08). Verified facts below were read from the
repo at this commit; re-verify anything that moves before acting.

**Non-goals (explicitly deferred):** Pydantic v3, HTTPX 2, TypeScript 7, zuvloop, free-threaded
(3.14t) builds, Python 3.15.

**Two facts that change the design:**

1. `uuid.uuid7()` is **stdlib only from 3.14**. On 3.13 it does not exist. UUIDv7 therefore cannot
   land before the runtime switch unless a third-party shim is added — not worth it.
2. SQLModel maps `UUID4` and `UUID` annotations to the **same** SQLAlchemy `Uuid` type. Verified on
   this venv: both produce `Uuid` → `CHAR(32)` on SQLite / native `UUID` on PostgreSQL. Changing the
   annotation is therefore **not a schema migration**; `alembic check` must stay clean.

## Phase B — Aware-UTC datetimes (largest diff; start on a branch now, merge inside the window)

Follow `docs/backend/UTC_MIGRATION.md` as the design source of truth. This plan sequences it; it
does not replace it.

### Task B1: Re-run the schema inventory against a fresh clone

**Files:** `docs/backend/UTC_MIGRATION.md` (update the counts table if it drifted)
```sql
SELECT table_name, column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public' AND data_type LIKE 'timestamp%'
ORDER BY table_name, column_name;
```
**Expected:** 122 rows / 39 tables at `c8f2a1b3d4e5`. Record any delta in the doc — the number is a
hard assertion, not a memo.

### Task B2: Introduce one clock helper and migrate producers

**Files:** `backend/app/utils/time.py` (new), then the 110 files using `datetime.utcnow()`.
```python
from datetime import UTC, datetime

def utcnow() -> datetime:
    """Timezone-aware UTC now. Replaces datetime.utcnow() (deprecated since 3.12)."""
    return datetime.now(UTC)
```
1. Add the helper with a test: `test_utcnow_is_timezone_aware_and_matches_system_clock`.
2. Codemod producers mechanically (`ruff` rule `DTZ` will find them once selected — for this phase,
   use `grep -rl 'datetime.utcnow' app | xargs` with a scripted rewrite; do not hand-edit 384 sites).
3. Replace `datetime.utcnow` **default factories and `sa_column_kwargs`** in `app/models/base.py`
   last — models sit on the boundary and will change again in Task B4.

**Acceptance:** `grep -rn 'datetime.utcnow' backend/app` → 0 hits; full suite green under both 3.13
and 3.14.

### Task B3: Fix comparisons and serialized boundaries

**Files:** `app/services/` (exploration, training, crafting, pregnancy, incidents, quests),
`app/db/session.py`, `app/schemas/`.
- Every comparison against a DB value must be aware-vs-aware; a naive literal will now raise
  `TypeError` instead of silently shifting.
- Exploration **JSON** timestamps (`position_as_of`, return deadlines) need the same treatment as
  typed columns — the doc calls this out and it is easy to miss.
- API responses gain `+00:00`. Decide deliberately: keep offset in responses (recommended) and
  update the frontend parsers if any assume a bare `Z`-less string.

### Task B4: Schema migration + compatible reader

**Files:** `backend/app/alembic/versions/<new>_aware_utc_timestamps.py`, model annotations.
- `ALTER COLUMN ... TYPE timestamptz USING <col> AT TIME ZONE 'UTC'` for all 122 columns; all
  existing values are naive-but-UTC by contract.
- Ship the compatible reader first (read naive, write aware) if the deploy cannot be atomic; keep
  the migration in the `maintenance_mode=true` path.
- Test against a **throwaway** Postgres 18 pod, never the `fallout` namespace: preserved instants
  under a non-UTC session TZ, nullable columns, deadline boundaries, enum labels.

### Task B5: ORM bump

```bash
cd backend && uv lock --upgrade-package sqlmodel --upgrade-package sqlalchemy
```
Target `sqlmodel==0.0.48`, `sqlalchemy==2.1.x`. Remove the `# Upper bound is the pre-3.0
compatibility boundary` comment in `pyproject.toml` and the Dependabot ignores for
`sqlmodel >=0.0.45` / `sqlalchemy >=2.1`.

**Acceptance:** `test_enum_drift.py` green (SA 2.1 named-type rework), `alembic check` clean, full
suite green. Update the naive-UTC convention docs: `README.md`, `AGENTS.md`, `app/models/base.py`.

### Task B6: Production-clone rehearsal

Restore a snapshot into an isolated namespace via `scripts/restore-drill.sh`, run B4's migration,
boot the new image, exercise a tick, then roll back to `v2.295.1` against the pre-migration

  plus `alembic check` is the test.
- Do **not** adopt the free-threaded build (`3.14t`); async app, GIL is not the bottleneck, wheel

**Acceptance for Phase C:** green CI on 3.14 alone, image smoke green, image built by the release
workflow reports `python --version` 3.14.x, full suite parity with the 3.13 baseline.

## Phase D — UUIDv4 → UUIDv7 (after C; stdlib `uuid.uuid7` requires 3.14)

### Task D1: Widen annotations without changing storage

Replace `from pydantic import UUID4` / `UUID4` annotations with `from uuid import UUID` across
`backend/app/models/`. 1726 references; scripted, then `uv run ruff check .` to catch stragglers.

**Why `UUID` and not `UUID7`:** `UUID7` is a validator — it would reject every existing v4 row on
load. `UUID` accepts both versions, which is exactly the mixed-population contract we need.
**Why not a migration:** SQLModel maps both to the same `Uuid` type (verified). `alembic check` must
report no diff; if it does, the annotation change is wrong, not the migration.

### Task D2: Emit v7 for new rows

**Files:** `backend/app/models/base.py`
```python
from uuid import UUID, uuid7

class BaseUUIDModel(SQLModel):
    id: UUID = Field(default_factory=uuid7, primary_key=True, index=True, nullable=False)
```
Keep existing rows as v4. No backfill — rewriting primary keys across 39 tables plus JSON
references is risk without benefit.

### Task D3: Choose per-call-site policy for the 43 explicit `uuid4()` uses

- **v7** where the ID is a database row and insert locality helps (e.g. `exploration_id`).
- **Keep uuid4** for storage/object keys and anything exposed as an unguessable capability
  (`conversation_service.py`, `broadcast_service.py` S3 keys) — v7 leaks creation timestamps into
  public URLs.
Add a one-line comment at each surviving `uuid4()` explaining the choice; otherwise a future sweep
will "consistency-fix" them.

### Task D4: Regenerate the frontend contract

```bash
cd frontend && pnpm types:generate
```
`src/core/types/api.generated.ts:10336` currently documents `Format: uuid4`; it becomes `uuid`. The
generated TS type stays `string`, so no component changes are expected — verify with
`pnpm test:unit` and a typecheck.

### Task D5: Regression tests

- `test_ids_are_uuid7_for_new_rows`.
- `test_mixed_v4_and_v7_rows_round_trip` (seed one explicit UUID4, load it, serialize it).
- `test_uuid7_ids_sort_by_creation_within_a_millisecond_burst` (RFC 9562 monotonicity).
- API test asserting a v4 ID from legacy data still resolves through every path that parses
  `UUID(...)`.

## Phase F — Release mechanics

1. **Freeze:** no gameplay merges during the window; branch `release/3.0` cut from master.
2. **Preflight:** `preflight_only=true` dispatch to capture production schema/capacity.
3. **Backup:** verify the `maintenance_mode=true` path takes and verifies the DB backup (it stops
   API + worker, backs up, migrates, restarts).
4. **Version:** one commit with a `BREAKING CHANGE:` footer so Semantic Release emits `3.0.0`. Do
   **not** hand-create the tag.
5. **Deploy:** merge → Release workflow builds images with `PYTHON_VERSION=3.14` → dispatch
   `deploy-hetzner.yml` with `image_tag=v3.0.0 -f run_migrations=true -f maintenance_mode=true`.
6. **Rollback artifacts:** pin `v2.295.1` images + the pre-migration snapshot; document the exact
   revert command in `docs/DEPLOYMENT.md`.
7. **Post-deploy:** API + frontend 200, pods 1/1 zero restarts, a real tick on a live vault,
   timestamps returning `+00:00`, a v4 legacy ID still resolvable, error-level logs empty for 10 min.
