using `backend/alembic-squash.ini`. The normal `alembic.ini` and every original

## Baseline

`app/alembic/baseline_versions/` contains the new root revision and frozen SQL.
The SQL was generated from the **empty database replaying the original history**,
not from the local application schema or player rows. It contains all PostgreSQL
enum labels, tables, defaults, indexes, constraints, 106 objective seeds and four
immutable v1 prompt seeds. The original `item_type IN (...)` check expression is
retained to avoid an equivalent but differently deparsed array cast on dump replay.

The baseline also creates the original environment-configured admin, demo user,
demo vault and map slot. Password hashes are generated at execution time; neither
password hashes nor local player data are embedded in the snapshot. Random
bootstrap IDs/timestamps/hashes need not equal another fresh installation.
Prompt IDs/content are preserved; objective seed content is compared apart from
the IDs generated by the original migrations. Historical player backfills apply
through the legacy history before adoption, while new databases start at their
final schema and seed state.

Example inspection and fresh-build commands, from the experiment's `backend/`:

```bash
uv run alembic -c alembic-squash.ini history
POSTGRES_DB=fallout_squash_fresh_20261020 ASYNC_DATABASE_URI= \
  uv run alembic -c alembic-squash.ini current
```

For a **new, empty scratch database**, replace the database name explicitly:

```bash
POSTGRES_DB=YOUR_EMPTY_SCRATCH_DATABASE ASYNC_DATABASE_URI= \
  uv run alembic -c alembic-squash.ini upgrade head
```

Adopting an existing database is a separate operation: complete the legacy chain,
inspect its schema against the reference, then explicitly stamp using the new
config. The clone experiment used `stamp --purge head`, followed by `upgrade head`.
The purge replaces the legacy revision marker without needing that revision in
the new graph. **Stamping does not fix schema drift or execute backfills.** The
clone was deliberately stamped as a disposable test even with its recorded drift;
this does not establish that stamping a real installation is ready.

The baseline refuses downgrade below itself. Later revisions can downgrade to
the baseline normally. To undo only this experiment's clone stamp before applying
any later changes, restore its legacy marker with the original config:

```bash
POSTGRES_DB=fallout_squash_clone_20261020 ASYNC_DATABASE_URI= \
  uv run alembic -c alembic.ini stamp --purge b7e3d9c1a5f2
```

## Existing drift discovered

The local database and a fresh legacy replay both reported `b7e3d9c1a5f2`, but
their schemas already differed before the squash:

- **26 column-property differences**, mostly missing server defaults locally.
- Local `exploration.unclaimed_loot` is nullable and has no default; the legacy
  chain creates it `NOT NULL DEFAULT '[]'::jsonb`.
- Local `objective.description` uses `text`; the chain produces unbounded varchar.
- Local `vaultslot` lacks the chain's `ix_vaultslot_id` index.
- Three foreign keys have different names; their referential actions match.
- Three enum types have the same labels but different sort orders. Column order
  and equivalent item-check expression rendering also differ.

These differences were recorded and left intact. A rollout needs a separate
decision about the canonical schema and any data-safe reconciliation migration,
plus checks of every maintained database's revision. The experiment demonstrates
baseline creation and lossless version-marker adoption; it does not claim that
the existing local schema is identical to a fresh installation or validate
PostgreSQL versions other than 18.
